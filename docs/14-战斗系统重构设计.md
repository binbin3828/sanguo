# 战斗系统重构设计（2026-09-29）

> 状态：设计稿；2026-09-29 已开始实现可玩首版。数值标为“建议值”的部分属于新版平衡方案，不冒充原 C 程序的原始配置。

## 1. 目标与范围

战斗应成为“战略上选人、选城、备粮 → 战场上看地形、走位、用兵种与计谋 → 战后真实改变城池和武将”的完整循环。首要平台是竖屏手机浏览器，保留以后移植微信小游戏的可能。进入战斗后，关键操作必须在一屏内完成；地图能看清、点得准，战果能明确反馈。

本阶段聚焦玩家参与的攻城与守城战。外交、剧情战役编辑器、多人对战和复杂动画不进入首版。AI 对 AI 的月末战争可继续战略层结算。战斗规则应独立于 DOM，未来换渲染容器时无需重写胜负和数值。

## 2. 原 C 程序与现版差距

证据主要来自本机旧源码 `/private/tmp/ibaye-original-review/src/`。源码中部分实际数值来自二进制资源，当前不能只凭旧设计文档推断其精确值。

| 项目 | 原 C 代码中的已核实行为 | 当前项目 | 新版决定 |
|---|---|---|---|
| 战斗地图 | `citycmdd.c` 以 `dCityMapId` 将 38 城关联到 7 类战斗地图，结合进攻方向布阵；地图由资源文件载入 | 所有战斗使用同一块 9×7 空白棋盘 | 建立可配置城池战场模板，首批 7 类，按城池与来路选择布阵 |
| 地形 | `fight.h` 定义草地、平原、山地、森林、村庄、城池、营寨、河流；`FgtCount.c` 有不同防御系数 | 森林由坐标公式临时生成，只减伤 | 每格显式地形；影响通行、移动消耗、防御、技能和目标争夺 |
| 单位 | 每方至多 10 将，6 兵种；有兵力、HP、MP、状态、移动力 | 进攻 1–3 将，守方最多 3 将；只看兵力和武力 | 手机首版保持 1–3 出征将，守方最多 3 将加 1 队驻军；完整兵种及战斗属性进入引擎 |
| 行动 | `FgtGenMove` 后还能下攻击、计谋、休息等命令 | 移动或攻击二选一，行动即结束 | 每单位每回合至多移动一次，再执行攻击/技能/待机之一 |
| 寻路 | `FgtCountPath` 按兵种与格子阻力找路径，单位阻挡 | 曼哈顿距离可直接跳到目标 | 加权寻路，显示可达格与路径，不能穿过敌军或障碍 |
| 攻击 | 兵种攻防系数、地形防御、兵种克制、武将属性参与伤害 | 固定公式，近战相邻 | 近战/远程范围、克制与地形修正、战前伤害预览 |
| 技能 | `SKILLEF` 含 MP、天气、双方地形、兵种、状态、粮草效果及 9×9 范围掩码；技能随兵种和等级解锁，另有特技 | 无 | 首批 10 个技能，配置驱动，显示可施放原因、范围、预估效果 |
| 天气 | 晴/阴/风/雨/冰雹，逐战斗日变化，影响技能 | 无 | 回合天气、下回合预报、地图和技能联动；随机种子固定于战斗 |
| 胜负 | 可夺城格、歼敌、主将失能、断粮、30 日守住 | 只看是否一方全部兵力归零 | 恢复多种胜负条件，移动端默认 12 回合，细则见下 |
| 战后 | 战损、粮草、经验、城池和俘虏按结果处理 | 部分兵力/城池/俘虏结算 | 唯一结算入口，任何胜负路径只应用一次结果 |

原版默认最长 30 日见 `varma.c:g_FgtBoutMax`。原 C 的 38 城→7 类地图映射见 `pconst.c:dCityMapId`，不是 38 张独立绘制地图。`data/dat.xml`列有 30 个技能名，但完整技能效果与范围不在该 XML 中；新版参数要明确作为自主设计和平衡数据维护。旧 `docs/04-战斗系统详细设计.md` 是早期参考稿，其中 BFS、地形消耗等描述不可视为已核实的 C 源码事实。

## 3. 玩家流程

1. **出征前**：延用“相邻城池、1–3 名有兵武将、本月每将一令”。选人面板新增兵种、兵力、预计粮草、目标城关卡类型、天气倾向与攻城难度。启动战斗前就锁定本月指令并分配战役 ID，避免退出页面重复出征。
2. **布阵**：进入目标城专属地图，在进攻边缘 2 行的高亮格安排武将；可一键按默认队形摆放。守方围绕城池、营寨部署，城市预备兵成为独立守备队，不再凭空代替所有武将。
3. **玩家回合**：点己方单位→显示可达格与攻击/技能目标→点格移动→选“攻击 / 计谋 / 待机”，或原地直接下令。允许在下令前撤销本单位移动；确认命令后不可撤销。全部单位行动完可自动提示结束，不强制自动结束。
4. **敌方回合**：敌军逐队行动；可加速或跳过非关键动画，关键战果（击溃、失守、夺城、断粮）暂停并短暂提示。
5. **回合结算**：粮草、持续状态、天气预报/切换、城池占领进度和胜负判定统一处理。战场上随时能查看目标说明、战斗日志、双方粮草与回合数。
6. **战后**：先显示战报（胜负原因、战损、俘虏、资源与城池变化），再回战略地图。失败和撤军不是同一个结果。

## 4. 关卡和地图

### 4.1 关卡定义

每次攻守一座城就是一关；历史剧本仍决定城池、武将、势力初始状态。关卡数据由 `targetCityId + sourceCityId + mode + mapTemplateId` 组成。城池映射先参考原版 7 类，再按城市特征微调阻塞物、桥、城门和守军布阵。例如：平原城、关隘、山城、林间城、水道城、河口城、都城。相同模板可复用，守备等级和天气倾向使不同城市不雷同。

**首版地图逻辑尺寸建议 10×8**：320px 宽手机单格约 32px，地图一屏完整可见，点按命中区可由格子和邻近留白扩展。相比现版 9×7 多出布阵和迂回空间；不依赖缩放和平移。大地图与镜头拖动留给后续扩展。每图必须有：1 个城池核心格、进攻部署区、守军部署区、至少 2 条合法进攻路径、可读的地形轮廓。狭路地图也要有一条风险更高的侧路，避免纯堵门。

| 模板 | 战术主题 | 典型选择 |
|---|---|---|
| 平原城 | 开阔接敌 | 骑兵冲击与弓兵火力位置 |
| 关隘 | 城门、营寨与侧道 | 强攻还是绕侧门 |
| 山城 | 高防山地、短捷径 | 步兵稳进或技能破局 |
| 林间城 | 森林掩护与窄道 | 伏击和反伏击 |
| 河道城 | 河流、桥、浅滩 | 水军走水路，陆军争桥 |
| 河口城 | 双水路与村庄 | 分兵、补给点争夺 |
| 都城 | 双层防线与城池核心 | 先拔营寨再攻核心 |

数据文件需明确 `width/height/terrain[]/objective/spawnAttackerByDirection/spawnDefender/landmarks/weatherWeights`。原版进攻方向用于布阵；新版从战略地图相邻城坐标计算来路，将地图旋转或镜像到相应方向。不可只换双方 x 坐标，否则桥和城门方向会错。模板数据制作时进行静态校验：两方不重叠、城池可达、所有合法兵种至少有一条可行路线、城池核心非部署格。

### 4.2 地形规则（首版建议值）

移动预算使用整数。下表是新版建议，不声称等于旧资源 `dFgtLandR`。不能通行的兵种须在界面显示原因；桥是河流格的地图标记，不新增第九类地形。

| 地形 | 陆军进入消耗 | 水军进入消耗 | 防御倍率 | 特殊作用 |
|---|---:|---:|---:|---|
| 草地 | 1 | 2 | 1.00 | 常规通行 |
| 平原 | 1 | 2 | 1.00 | 骑兵冲锋加成 |
| 山地 | 3；骑兵 4 | 3 | 1.30 | 弓兵射程优势；骑兵受限 |
| 森林 | 2；骑兵 3 | 3 | 1.15 | 远程受击减轻；火攻风险 |
| 村庄 | 1 | 2 | 1.10 | 首次占领给少量粮草，防刷取 |
| 城池 | 2 | 3 | 1.50 | 攻守核心；守军可获得固定防守补正 |
| 营寨 | 1 | 2 | 1.20 | 一方控制后可提供少量回合补给 |
| 河流 | 陆军不能进入，桥/浅滩例外 | 1 | 0.80 | 桥上陆军防御较低 |

原 C 明确的地形防御倍率为 `[1,1,1.3,1.15,1.1,1.5,1.2,0.8]`（`FgtCount.c:TerrDfModu`）；保留这组易读且有差异的值。移动消耗按现代地图重配。城池/营寨的额外补给效果是新版创新。

## 5. 单位、移动与行动

六兵种保留原版：骑兵、步兵、弓兵、水军、极兵、玄兵。基础移动力采用 C 常量 `5/4/4/5/6/3`，装备速度加成后最多 8。兵种身份使用现有武将 `armsType` 和装备变兵种效果；没有配置时按步兵处理并标记数据缺失。首版不新增“统率”等战略属性。

每个战斗单位保存：`unitId, personId?, side, troopType, troops, hp, maxHp, mp, maxMp, x, y, status[], moved, acted, initialTroops`。HP 表示武将临场战力，兵力是部队数量。`troops=0` 或 `hp=0` 均算退出战场，但战略上的武将是否被俘应由战后规则决定，不直接等同阵亡。HP/MP 初始值可参考 `FgtCount.c:CountBaseAttr` 的属性公式，并以开战前体力快照计算，避免扣出征体力后重复惩罚；首版数值需在战斗模拟中调平。

路径算法采用 Dijkstra：四方向、无对角穿越、累计地形消耗、己军占据格可经过但不可停留、敌军格不可经过，地图边界/阻塞不可进入。若“穿过己军”导致视觉不清，首版可改为所有占据格都阻挡，数据表只需一处开关。高亮仅来自引擎返回的合法目标，UI 不再另算曼哈顿距离。点可达格后画出完整路径；点敌军或技能目标前显示目标数据与行动后风险。状态“定身”禁止移动，其余状态按技能定义影响攻击或计谋。

行动顺序固定为“可选移动 → 1 个主命令”。主命令为普通攻击、计谋、待机。攻击或计谋之后不可再移动；原地攻击可行。移动被撤销只允许在尚未下主命令时。AI 遵守同样规则。回合开始清空 `moved/acted`，持续状态在统一阶段递减。

## 6. 攻击、技能、天气

### 6.1 普通攻击

| 兵种 | 基础攻击范围 | 战术定位 |
|---|---|---|
| 步兵 | 相邻 1 格 | 稳定守线，较高防御 |
| 骑兵 | 相邻 1 格 | 平原直线走位后冲锋；山林劣势 |
| 弓兵 | 距离 2–3 格 | 远程压制，贴身时攻击受限 |
| 水军 | 相邻 1 格；水路可到达 | 河道机动优势 |
| 极兵 | 相邻 1 格 | 高机动突击，粮耗略高 |
| 玄兵 | 距离 1–2 格 | 计谋型，低兵力正面输出 |

距离按格子最短路的几何距离判定，攻击可视线另算；弓兵被山、城墙、单位挡住时要给出“射线被遮挡”的反馈。具体阻挡规则在模板规则中配置，避免假装一切可直射。普通攻击现按 iBaye `FgtCount.c:BuiltAtkAttr/CountAtkHurt` 的结构计算：武力、智力、等级、兵种攻防系数、各兵种地形位移修正、目标地形防御、兵力除以 8、兵种克制，最后加 10。原版 `FightSub.c:FgtDrvCmd/FgtAtkAction` 只执行一次普通攻击，没有自动反击。手机版规则另外保留 30% 概率的轻微反击，要求守方仍存活、尚未行动、尚未反击、未定身且攻击范围覆盖来袭者；伤害为普通攻击的 25%。切换经典范围时关闭这项手机版反击。贴身弓兵减伤、雨雪弓兵减伤、桥梁与奇门效果仍是新版规则。预览和飘字显示实际可损失兵力。

`FgtCount.c` 的兵种攻系数 `[1,.8,.9,.8,1.3,.4]`、防系数 `[.7,1.2,1,1.1,1.2,.6]` 和地形倍率已接入普通攻击。技能仍采用独立的手机版伤害公式；受击同时削减兵力与少量 HP，飘字显示实际伤兵。

### 6.2 技能

首批从原版 30 个名称中选 10 个，形成可理解的战术组合。技能表字段：`id, name, allowedTroops, minLevel, mpCost, targetType, rangeMask, legalWeather, legalCasterTerrain, legalTargetTerrain, effect, status, accuracy, animationKey`。从 C 的配置结构借鉴能力，但具体倍率由新版定义。不可施放时按钮仍可查看说明，并标注缺 MP、天气不符、地形不符、等级未到或目标无效。

| 技能 | 作用建议 | 主要约束/选择 |
|---|---|---|
| 冲锋 | 骑兵直线突击，按已移动距离加伤 | 山地/森林不可触发加伤 |
| 飞矢 | 弓兵单体远射 | 雨、冰雹命中较低 |
| 箭雨 | 小范围多目标低伤 | MP 较高，友军不能成为目标 |
| 火攻 | 森林/营寨目标加伤并留 1 回合火格 | 雨/冰雹不可施放，风增强扩散 |
| 落石 | 山地施术，对下方目标高伤 | 施术者须在山地 |
| 水淹 | 河流附近减速及伤兵 | 河流目标或雨天增强 |
| 定身 | 单目标 1 回合不可移动 | 可被智力抵抗；不取消已下命令 |
| 援兵 | 回复友军少量兵力，上限初始兵力 | 消耗施术方粮草，不能无限刷兵 |
| 奇门 | 友军 1 回合防御提高 | 不能叠加同类状态 |
| 天变 | 改变下一回合天气候选 | 君主/特技武将，消耗较高 MP |

这些技能的实际威力、可用兵种和解锁等级须形成一个表格资源；不可把 `dat.xml` 的技能名称表误当成完整效果表。若首版只做 6 个技能，优先保留“冲锋、飞矢、火攻、定身、援兵、天变”并确保其余技能 ID 可扩展。战斗中不能随意给所有武将全部技能：先按兵种+等级生成常规技能，再叠加特技；武将特技缺配置时不虚构其身份。

### 6.3 天气

五类天气与旧版一致：晴、阴、风、雨、冰雹。每次战斗以关卡天气权重抽初始天气；每回合开始从与当前天气关联的权重表抽下一天气，限制极端连续次数。顶部常驻显示“本回合天气”和“下回合预报”（预报确定且已写入战斗状态）。天气对普通攻击只做轻度修正，主要影响计谋可用性与命中：雨抑火、风助火和弓箭、冰雹减远程、阴天利于潜踪类后续技能。玩家在确认前就能看到效果，不靠暗骰猜。天气变更写入日志，并使对应地形效果随回合更新。

随机数以 `battle.seed + battle.rngState` 驱动；战斗存档恢复后得到同一序列，预览不消耗随机数。所有伤害、命中、天气都通过同一可复现随机入口。

## 7. 胜负、粮草与战略结算

### 7.1 胜负规则

玩家进攻：消灭敌方所有有效单位、击溃敌主将，或占据城池核心并守到敌方行动结束即胜。只走进空城格不立即结算，给守军一回合夺回机会。玩家防守：消灭敌军、击溃敌主将、守满第 12 回合，或敌方粮草耗尽即胜。双方粮草在回合结束扣除；扣完时先完成当前回合，再在下回合开始判负，避免同一瞬间出现无法理解的结果。双方同时归零等冲突按“攻方失败”处理。战斗上限 **12 回合** 是手机节奏的新版选择；原版 30 日留作自定义难度参数。

主将默认是出战面板标识的第一位武将，布阵前可以更换一次；守方取太守或战力最高可战武将。守备队没有武将 HP，也不能成为主将。城池核心与主将两条胜利路径会显著改变战术目标。撤退要单独确认，按现有 20%/有坐骑免损规则起步，但重新平衡损失并明确显示；撤退保留月令已执行。

### 7.2 粮草

战斗开始时从出征城、守城各自粮食中划出战役补给，建议 `min(城内粮食, ceil(参战兵力/250) × 14)`；每回合各扣 `ceil(存活兵力/250)`，极兵有少量额外粮耗。结算后未用粮草返回所属城。村庄/营寨、部分技能可改变战役补给，不直接复制城市总粮。如果不足 1 回合所需补给，出征前明确阻止并提示补粮；守城零粮则允许进入战斗并在规则规定的时点触发断粮。这里是新版建议值，正式实装应按四个历史剧本初期粮兵比例校准。

战后统一提交：兵力回写到原武将、战损扣除，胜利时移动出征武将至目标城并变更城主，守城成功则留原城；俘虏、释放、忠诚与现有战略规则接通；经验按造成伤害和胜负奖励分配。战斗状态在结算成功后清除。禁止 UI 和引擎分别修改城池，以免重复奖励或重复被俘。无主城市若触发战斗，仍应有预备守军和夺城目标。

### 7.3 AI 进攻玩家

现有月末 AI 攻城在 `GameModel.js` 的战略层直接结算。重构后，**AI 进攻玩家城市**应生成待处理守城战，月末事件弹窗播报敌军来袭，玩家进入战场指挥守方；AI 对 AI 的攻城继续快速结算。处理守城战前暂停月末后续事件；战斗结束才继续本月结算，避免同一个月中城池状态穿越。此接口与玩家主动出征共用同一 `BattleEngine`，仅交换玩家攻守身份和胜利条件。

## 8. 战场 AI

AI 以合法动作列表决策，不单独写一套作弊移动。每单位生成可达位置与可执行命令，对候选行动打分：立即取胜/阻止失城最高，击溃目标次之，其次为克制、高地/城池、友军掩护、粮草与避免被围攻。守军主将优先守城，不会为了追残兵离开核心；攻方对城池目标保持推进压力。普通难度只搜索“移动+动作”一步，困难难度在同一接口增加风险评估。AI 决策日志仅作开发诊断，玩家只看战场行动与关键提示。

战斗应没有无意义拖回合：若连续 2 回合双方无伤害和无核心推进，提示“战线僵持”；AI 至少有一路尝试夺取目标。预期普通战斗 5–10 分钟，大势已定时允许快速播放敌方回合。

## 9. 手机界面

竖屏以 `100dvh` 加安全区内边距布置：顶部一行回合/天气/双方粮草与胜利目标；中部完整 10×8 战场；下部固定单位卡与“移动、攻击、计谋、待机、结束回合”操作条。地图不占纵向滚动文档，页面禁止手势误触滚动；弹出的技能说明和战报采用底部抽屉，不遮住待选目标区域。横屏可扩大格子并把操作条放侧面。以 320px 宽手机为硬约束：触控目标至少可感知且易点，单位拥挤时点格先弹目标选择，不强迫在 32px 方格内精准点头像。

格子状态有四种明确色层：可移动、可攻击、技能可选、危险范围，不能只靠颜色区分，需有纹理/图标。选中单位显示兵种、兵力、HP/MP、地形增益、行动状态；长按敌军/地形查看详情，单击按当前行动模式执行。每次有破坏性操作先出预估与确认按钮；同一动作不需多次弹窗。战场日志只记录可理解事件，如“赵云从平原冲锋张辽，伤兵 132；山地守御减伤 25%”。

视觉先复用 `src/assets/images/terrain/` 与 `src/assets/images/army/` 的现有 SVG，统一规格、描边和阵营色；后续替换成像素瓦片与角色帧时不改战斗数据。动画只为表现，不能承担规则判断。

## 10. 技术边界与数据结构

建议拆出：

```text
src/game/battle/BattleCatalog.js    // 地图、技能、兵种、天气静态配置
src/game/battle/BattleEngine.js     // 纯状态机：合法动作、执行、回合、胜负
src/game/battle/Pathfinding.js      // 地形权重与阻挡
src/game/battle/BattleAI.js         // 使用同一个合法动作接口
src/game/battle/BattleAdapter.js    // 从战略状态进入战斗与提交结果
src/ui/BattleScreen.js              // 只渲染与发意图，或在现有 main.js 中先隔离模块
```

引擎接口建议 `createBattle(context)`, `getLegalActions(state, unitId)`, `previewAction(state, action)`, `applyAction(state, action)`, `endTurn(state)`, `getBattleResult(state)`。每次 `applyAction` 返回新状态与事件列表；UI 只显示事件。状态至少含 `version, battleId, mode, phase, round, mapId, seed, rngState, weather, forecast, supplies, units, objectiveProgress, events, result`。`GameModel` 只管理“战略→战斗→战略”的接缝。这样既能在浏览器 localStorage 保存，也能日后接微信小游戏存储 API。

旧战略存档没有这些字段：恢复时保持 `battle=null`；新增的战斗中存档使用版本 2 验证，不能把旧 9×7 单位状态误读为新地图。手机被打断时自动保存当前战斗快照（每次已确认动作之后），回到游戏优先恢复战斗；手动存档也允许在战场使用。一次性结算用 `battleId` 和已提交标志保护。既有 3 个存档槽和导入导出应继续可用。

## 11. 实施顺序与完成标准

| 阶段 | 交付内容 | 可玩的验收场景 |
|---|---|---|
| A. 引擎骨架 | 地图数据、单位状态、合法移动/行动、城池核心、统一结算；保留现有画面作过渡 | 从相邻城出征，移动后攻击，夺城/全歼/撤军均正确回到战略图 |
| B. 真实战术 | 7 类地图、8 地形、6 兵种、攻击范围、地形与克制、战前预览 | 同一组合在平原与山地的最优打法不同，河道有争桥选择 |
| C. 技能天气 | MP、首批技能、状态、五种天气、确定性随机 | 雨天禁火攻，山地落石可用，定身和援兵影响下一回合 |
| D. 守城与 AI | AI 攻玩家触发可操控守城、目标型战场 AI、粮草、12 回合 | 玩家能以守城拖满回合获胜，AI 会争夺城池核心 |
| E. 手机打磨 | 单屏战场、布阵、战报、自动恢复、动效音效与数值平衡 | 320px 宽设备无需页面滚动，可完成整场战斗并重进恢复 |

每阶段以真实流程核查：相邻城出征、无主城、主将失能、断粮、退兵、目标占领、多人参战、连续月令、AI 来袭、存档恢复。数值以至少 3 个典型剧本局面（初期弱势、均势、强势）做人工试玩平衡。不要在引擎未闭环前投入大量美术制作。

## 12. 明确保留待定的平衡参数

首版先固化规则，以下参数集中配置而非散在代码：战斗上限 12、每图 10×8、首批技能数量、粮草系数、反击倍率、技能命中、天气转移概率、城池守御补正、俘虏概率。旧 C 的技能效果依赖未解出的资源文件，须把“源代码已验证的机制”和“新版自行设计的数值”分别标注在配置注释和后续变更记录中。

## 13. 当前实现进度
