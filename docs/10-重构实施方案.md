# 三国霸业重构实施方案

更新：2026-09-29

## 一、产品目标

面向手机浏览器优先制作一款以步步高电子词典《三国霸业》为核心参考的单机三国 SLG。保留「选剧本和君主、看天下城池、经营与招将、逐月行动、从邻城出征、战棋交战、统一天下」的游戏节奏。界面采用清晰的现代排版、保留像素地图和战棋的辨识度，同时兼容桌面浏览器。将来可能发布微信小游戏，现阶段先完成手机网页的完整可玩流程。

参考项目：

- [BGWP/iBaye](https://gitee.com/bgwp/iBaye)：经典《三国霸业》的 C 语言多平台移植，用于核对游戏规则和原始数据。
- [kvinwang/baye-alpha](https://github.com/kvinwang/baye-alpha)：H5 移植前端，用于参考完整游戏流程。
- [zhs007/sanguo](https://github.com/zhs007/sanguo)：另一款 C++ 三国 SLG，只用于参考工程组织，不作为《三国霸业》规则依据。

本项目的 `data/dat.xml` 沿用已有剧本数据。游戏逻辑、界面和战斗数值应逐项核对 iBaye 后再称为「原版还原」。

## 二、工程现状与取舍

早期重构曾并存多套入口、数据字段和未接通的指令。当前运行版本统一使用 `src/main.js`、`src/game/` 与 `data/dat.xml`；未接入的旧系统、模型、UI 和旧测试已删除，避免误把旧实现当成现行规则。原版规则以 iBaye 源码对照记录为依据。

当前重构采用：

- `src/game/GameData.js`：解析 XML 剧本，创建结构一致的城池和武将初始数据。
- `src/game/MapData.js`：集中存放 38 城的位置与相邻路线。
- `src/game/GameModel.js`：单一可序列化状态、城市指令、月末结算、AI、战斗与胜负。
- `src/main.js`：页面流程、地图、城市面板、战场交互及浏览器本地存档。
- `styles.css`：响应式界面。

手机交互使用横向拖动的地图、大尺寸城池列表与原生选择器、可关闭的城池底部面板，以及战斗底部固定操作栏。地图上的密集城池点用于观察局势；城池列表与选择器提供可靠的触控入口。

现有原始 XML 不含完整的可直接使用的驻军初始化和战棋地图；当前驻军、战斗伤害、经济结算与 AI 是重构预览规则。它们需要按下述阶段与 iBaye 逐项对照，不能视为原版公式。

## 三、需求与分阶段交付

### 阶段 1：可玩的战略闭环（当前已接通）

1. 从四个剧本选择君主，载入 38 城和归属关系。
2. 在地图查看城市、武将、相邻城市和资源。
3. 每名武将每月接一项任务，同城多名武将可分别执行开垦、招商、征兵或寻访。
4. 结束月份后进行城市收入、粮食消耗、人口变化和 AI 行动。
5. 从己方城池进攻相邻目标，进行 9×7 的简化战棋战斗，结算占城或撤军。
6. 在战略地图保存和读取三个本地存档位，支持导出与导入，统一天下或失去全部城池时展示结果。

验收路径：在 320px 与 390px 宽的手机视口中，190 年选择曹操 → 从城池列表打开濮阳 → 选择一名武将寻访 → 再选另一名武将开垦 → 结束月份并查看寻访结果 → 选可用武将进攻许昌 → 战斗移动与攻击 → 战斗结算 → 保存 → 刷新并读档，日期、城池归属、武将任务和资源一致。游戏操作不依赖悬停或物理键盘。真机触控与性能仍需在手机上补验。

### 微信小游戏的后续适配边界

现有 `GameModel.js` 和 `MapData.js` 只使用 JavaScript 数据结构，后续可继续复用。`src/main.js` 使用网页 DOM，`GameData.js` 使用网页的 `fetch` 和 `DOMParser`，存档使用 `localStorage`；若正式发布微信小游戏，需要针对届时平台的运行环境另做入口、渲染、剧本数据加载与存档适配，并在目标平台验证触控与性能。当前手机版网页不等同于已适配微信小游戏。

### 阶段 2：规则对照与数据完整性

1. 对照 iBaye 确定原版城池、武将、道具、兵种、指令、行动耗时与数值公式。
2. 建立原版规则与现代化改动清单。每一条有来源、实现位置和设计理由。
3. 补齐中立城、在野武将、俘虏、装备与武将去向，杜绝重复归属或消失。
4. 已有版本化存档、三个存档位及导出导入；仍需建立可重复的随机种子与更完整的数据校验。

验收：四个剧本能加载；每城、每将具有唯一 ID；任意占城、招揽、败退后数量与归属守恒；读档后继续游戏的结算一致。

### 阶段 3：完整战略玩法

接入原版内政、外交、军事指令，执行者与体力、持续时间、粮草、移动和资源运输。AI 必须使用同样的行动规则，并能发展、外交和出征。加入事件、灾害和胜负条件。

验收：玩家与 AI 的指令遵循同一规则；一局可以在任意剧本、任意君主下持续多年推进，不发生资源负数、死循环或不可恢复状态。

### 阶段 4：完整战斗与体验

将简化战棋替换为经原版对照的兵种、地形、天气、技能、攻击范围、粮草和武将经验系统。为地图和角色建立统一像素资源规范；增加动画、音效、键盘操作、移动端触控反馈与清晰的战斗信息。

验收：进攻与守城、胜利与失败、撤退与俘虏、回到战略地图的状态转移完整；桌面与手机均能完成一场战斗。

## 四、当前优先问题

| 优先级 | 问题 | 完成条件 |
| --- | --- | --- |
| P0 | 现用规则和原版规则尚未逐项核对 | 形成规则差异表，确定保留与调整的数值 |
| P0 | 旧系统代码与新入口并存 | 每迁移一块功能即移除对应无效实现和过时文档声明 |
| P1 | 存档仍依赖本地浏览器 | 已有多存档位、导出导入、旧存档迁移；后续补导入内容校验与目标平台存储适配 |
| P1 | 战棋与 AI 仍为简化实现 | 原版对照后接入兵种、技能、地形和更可靠的 AI |
| P2 | 地图为抽象城池网络 | 制作正式地图资源与统一的像素视觉规范 |

开发进度按玩家可完成的流程记录，不再按文件数量或类名统计。

## 五、接下来的工作顺序

当前已补齐武将逐人接令、批量选将、即时与月末执行回报，并对照 C 源码实现了征兵兵量和费用限制，以及治理、出巡的即时效果。其余工作按对可玩性的影响排序：

1. **保存战局**：三个存档位、导出与导入、旧格式迁移已经接通。后续补存档内容校验和微信小游戏的存储适配；手机更换浏览器前可自行导出备份。
2. **武将与城池数据守恒**：已拆分城市后备兵和武将带兵数，增加玩家的「分配」操作，并让出征使用参战武将实际带兵。占城与战败后已区分在职、在野、俘虏，并接入月末招降。下一步补齐战后逃脱、处斩、流放和完整武将去向规则，并检查各类战斗中的兵力守恒。
3. **原版战略规则**：继续对照治理、巡查、运输、移动、外交等命令，统一玩家与 AI 的执行约束。
4. **战斗与收支**：对照原版兵种、地形、粮草、技能和每月经济；替换当前简化战棋、AI 和收支公式。
5. **手机视觉与发布准备**：真机触控检查、像素资源规范、音效与反馈；核心玩法稳定后再适配微信小游戏运行环境。

以上是后续迭代，不代表本轮征兵改动已通过真机验收。
